# 수직 슬라이스 작업 지시서 — #7 건물 검색 API + #8 iOS 검색 화면

이 문서는 맥북의 Claude Code 세션을 위한 지시서다. 저장소 `docs/slice-7-plan.md`에 두고, 새 세션을 열 때마다 이 문서를 먼저 읽는다.

## 0. 이 작업이 무엇인지 (가장 중요한 배경)

이 저장소는 교재 「생성형 AI를 활용한 소프트웨어 개발」(전광일·최종무, 2026)의 **공개 예제 저장소**다. 여기서 만드는 코드는 제품이 아니라 **교재 Ⅹ~ⅩⅢ장의 원재료**다. 교재 본문이 이 저장소를 실명 링크로 가리킨다.

그래서 보통의 개발과 두 가지가 다르다.

**첫째, 과정이 결과보다 중요하다.** 실패, 막힌 지점, 잘못 든 길, 되돌린 결정을 지우지 말고 남긴다. Ⅷ장에서 가장 값진 내용은 파이프라인이 잘 돌았다는 사실이 아니라, 1차 실패의 진짜 원인이 `package-lock.json` 부재였다는 발견이었다. 그런 것이 이번에도 나오면 그게 교재의 핵심 장면이 된다. **깔끔하게 정리된 최종 결과만 남기면 이 작업은 실패한 것이다.**

**둘째, 증거를 남겨야 한다.** 아래 6절의 증거 파일 목록을 작업하면서 채운다. 나중에 재구성할 수 없는 것들이다(테스트 빨간불 출력, 그때의 프롬프트와 이유, CI 실행 링크).

## 1. 슬라이스의 경계

교재 집필 일정 때문에 제품 전체는 구현하지 않는다. **이슈 #7과 #8 하나의 실만 앱에서 DB까지 관통시킨다.**

**포함**
- `server/` — 건물 검색 API 엔드포인트, 검색 인덱스 마이그레이션, 오류·경계 응답, 테스트
- `ios/` — 검색 화면(SwiftUI), API 호출, 결과 목록, 접근성(VoiceOver) 대응, 테스트
- 고정 시드 데이터 (아래 3절 참조)

**제외 (설계 문서에만 존재하고 구현하지 않는다)**
- 현장 브리핑 엔진 E2 — 나침반·위치가 걸려 시뮬레이터로 절반만 검증된다
- 수집 배치 #10, 검수·게시 관리자 웹 #11 — 공공데이터 API 호출은 이번 범위 밖
- 인증 #13, 사전 학습 E4, 탐색 보조 E5

교재는 이 경계를 명시한다. 없는 것을 있는 것처럼 쓰지 않는다.

## 2. 작업 방식 (저자와 합의된 규칙)

- **단계별 진행 엄수.** 각 단계를 마치면 저자에게 보고하고 confirm을 받은 뒤 다음 단계로 간다. 여러 단계를 몰아서 진행하지 않는다.
- 결정이 필요한 지점에서는 **선택지와 트레이드오프를 제시하고 저자가 고르게 한다.** 임의로 정하지 않는다.
- 수치에는 출처를 단다. 근거가 없으면 '팀 추정'이라고 쓴다.
- AI(너 자신)의 제안을 저자가 기각하면 **기각 기록을 남긴다.** 무엇을 제안했고 왜 기각됐는지가 교재의 재료다.
- 용어는 교재 공식 명칭을 쓴다. 새 낱말을 짓기 전에 `docs/`와 교재 용어집을 먼저 확인한다.

## 3. 0단계 — 현황 파악 (여기부터 시작한다)

코드를 한 줄도 쓰기 전에 아래를 읽고 저자에게 요약 보고한다.

- `CLAUDE.md`, `README.md`, `docs/SETUP-RUNBOOK.md`
- `server/` 골격 전체 — package.json, 기존 파일, 테스트 설정
- `.github/workflows/merge-gate.yml` — 잡 이름, 경로 필터, 실행 조건
- `.github/ISSUE_TEMPLATE`, PR 템플릿
- `docs/adr/ADR-001~006` — 특히 001(분리 구조), 002(스택), 005(방위 보정), 006(응답 캐시)
- `docs/definition-of-done.md`
- 이슈 #7과 #8의 제목·본문·라벨·마일스톤 (`gh issue view 7 8` 또는 GitHub API)

보고에 포함할 것: 서버 골격에 이미 있는 것과 없는 것, 테스트 러너가 무엇인지, `server-test` 잡이 실제로 무엇을 실행하는지, `ios/` 디렉터리의 현재 상태(플레이스홀더인지 Xcode 프로젝트가 있는지).

**이 단계에서 로컬 환경도 함께 확인한다.** Node 버전, PostgreSQL 설치 여부(Homebrew), Xcode 버전과 사용 가능한 시뮬레이터. 없는 것은 설치하되, 설치 과정을 `docs/dev-setup.md`에 기록한다 — 학생이 따라 할 문서가 된다.

## 4. 1단계 — 저자 결정이 필요한 세 가지

0단계 보고와 함께 아래 셋을 질문한다. 답을 받기 전에 설계로 넘어가지 않는다.

**① 시드 데이터를 무엇으로 채울 것인가.** 한국공학대 실제 건물명과 대략의 좌표를 저자가 제공할 수 있는지, 아니면 가상 캠퍼스로 갈지. 실제 데이터가 좋지만 없으면 가상으로 하고 교재에 그 사실을 밝힌다. 건물 수는 20~30건이면 충분하다(밴드별 5개 상한과 "외 N개" 동작을 시험하려면 반경 150m 안에 5개 이상이 몰린 구역이 하나는 있어야 한다).

**② 별칭 검색을 슬라이스에 포함할 것인가.** 별칭 등록·수정은 이슈 #12로 따로 있지만, 검색 품질의 핵심이 별칭 매칭이다. 읽기 쪽만 포함하고 등록 화면은 제외하는 절충을 권한다.

**③ Ⅺ장 관통 예제 교체 확인.** 교재 Ⅺ장은 원래 '주변 브리핑' 구현이었으나 브리핑 엔진은 실물로 만들기 어렵다. Ⅺ장 예제를 #7 검색 API로 바꾸는 안을 저자가 이미 검토 중이다. 확정 여부를 확인한다.

## 5. 2~6단계 — 작업 순서

각 단계는 저자 confirm 후 진행한다.

**2단계 상세 설계.** ERD(건물, 별칭, 게시 상태 전이만 — 브리핑 문안까지 포함할지는 저자에게 확인), 검색 API의 OpenAPI 명세, 앱→서버→DB 시퀀스. 검색 구현 방식(pg_trgm 대 ILIKE+인덱스)을 여기서 **결정하고 근거를 ADR 후보로 정리한다.** 새 ADR이 필요하면 번호는 007부터다(006까지 사용 중). 산출물은 `docs/`에 커밋한다.

**3단계 마이그레이션과 시드.** 스키마를 실제로 올리고 시드를 넣는다. 로컬에서 `psql`로 대표 질의를 몇 개 돌려 보고 결과를 기록한다. 이 단계에서 설계의 허점이 드러나면 그것도 기록한다.

**4단계 테스트 먼저.** 구현 전에 테스트를 쓰고 **실행해서 빨간불을 확인한다.** 이 출력이 ⅩⅡ장의 핵심 증거이므로 그대로 파일로 저장한다. 테스트 목록에는 정상 경로뿐 아니라 경계와 오류(빈 질의, 한 글자 질의, 결과 없음, 상한 초과, 게시되지 않은 건물 제외, 잘못된 파라미터)를 반드시 포함한다.

**5단계 구현.** 완료 조건을 명시한 뒤 구현한다. 서버 먼저, 그다음 iOS. 300줄 상한을 지키고 넘으면 PR을 쪼갠다. diff에서 요청하지 않았는데 딸려 온 변경은 분리하거나 되돌린다. 초록불이 될 때까지의 시행착오를 남긴다.

**6단계 PR과 파이프라인.** 브랜치 이름은 `feature/7-search-api`(iOS는 `feature/8-search-screen`). PR 템플릿을 성실히 채운다 — 특히 'AI 사용 내역'과 '이해하지 못한 부분'은 형식적으로 쓰지 말고 실제로 이해하지 못한 것을 적는다. 그것이 교재가 가르치는 정직한 무지다. CI가 도는 것을 확인하고 실행 링크를 기록한다.

## 7. 저장소 규칙 (어기면 교재와 어긋난다)

- **main에 직접 푸시할 수 없다.** 브랜치 보호가 걸려 있다. PR 필수, 승인 1인 필요, 필수 체크 `gate`, 관리자 포함 강제.
- **머지는 혼자 할 수 없다.** 승인 1인 요건 때문이다. 저자가 Settings → Branches의 규칙 80789141에서 'Do not allow bypassing'을 잠시 해제해야 머지할 수 있다. **보호 규칙을 직접 끄지 말 것.** 저자에게 요청하고, 머지 후에는 "아직 해제 상태"임을 반드시 보고해 원복을 받는다.
- **이슈 번호를 함부로 만들지 않는다.** #1~#24가 교재 본문과 그림에 번호 그대로 실려 있다. 새 이슈를 만들면 번호가 밀리지는 않지만, 교재 서술과의 정합을 먼저 확인한다.
- **기존 파일을 지우거나 이름을 바꾸지 않는다.** 교재가 경로를 실명으로 가리킨다.
- 커밋 메시지는 기존 관례를 따른다: `feat(server): ...`, `test(server): ...`, `docs(adr): ...`.
- ADR을 새로 쓸 때는 기존 형식을 따른다. 파일명 `ADR-00N-{영문슬러그}.md`, 본문은 제목 줄 + `상태:` `맥락:` `결정:` `근거:` `배제한 대안:` `트레이드오프:` 한 줄 라벨. `##` 소제목 형식이 아니다.

## 8. 산출물 표기 등급 (교재 정직성 규약)

교재에 실릴 모든 예시는 아래 셋 중 하나로 분류된다. 작업 중 애매한 것이 생기면 저자에게 알린다.

- **실물** — 저장소·CI에 존재하고 링크로 확인 가능. 표기 없음.
- **재현** — 실제로 실행한 결과를 지면에 맞게 줄인 것. "발췌" 표기.
- **가정** — 실행하지 않고 구성한 것. "(가정)" 표기와 근거 각주.

**코드 예제는 반드시 실행해 본 것만 싣는다.** 실행하지 않은 것은 코드 블록이 아니라 의사코드나 서술로 처리한다. 학생이 따라 쳤을 때 안 돌아가는 코드가 하나라도 나오면 책 전체의 신뢰가 무너진다.

## 9. 이 세션이 끝날 때

작업이 끝나거나 중단되면 `docs/slice-7/00-status.md`에 현재 상태를 남긴다. 어디까지 했고, 다음에 무엇을 할 차례이고, 미결 질문이 무엇인지. 교재 집필 세션(별도 대화)이 이 파일과 증거 파일들을 읽어 Ⅹ~ⅩⅢ장 본문을 쓴다.
