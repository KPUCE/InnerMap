# ADR-007 건물 검색 구현: pg_trgm 부분일치 + 하버사인 거리 정렬
상태: 채택 (Ⅹ장, 2026-07) · 슬라이스 #7
맥락: #7 검색 API는 질의로 게시 건물의 이름·별칭을 부분일치로 찾아 현재 위치 기준 거리순 최대 10건을 돌려준다(AC). 두 하위 문제 — 텍스트 부분일치의 인덱싱과 거리 정렬 — 의 구현 수단을 정해야 3단계 마이그레이션을 올릴 수 있다. 개발 시드는 19건(`docs/slice-7/seed-buildings.md`, OSM/ODbL)이나 운영 척도도 함께 고려한다.
결정: ① 텍스트 매칭은 `pg_trgm` 확장의 GIN 인덱스(`gin_trgm_ops`)를 `building.name`과 `building_alias.alias`에 두고 `ILIKE '%q%'` 부분일치를 가속한다. ② 거리 정렬은 `lat`·`lng`(double precision) 컬럼에 하버사인 식을 SQL에서 계산해 `ORDER BY distance ASC LIMIT 10`으로 한다. PostGIS는 도입하지 않는다.
근거: ① `ILIKE '%q%'`는 선행 와일드카드라 일반 btree 인덱스가 먹지 않는다 — 부분일치를 인덱싱하는 표준 수단이 trigram GIN이며, 별칭도 동일 방식으로 인덱싱된다. ② 시드가 19건이고 캠퍼스 범위가 남북 442m·동서 402m로 좁아 하버사인 순차 계산으로 충분·정확하다. PostGIS를 배제해 확장 의존을 `pg_trgm` 하나로 줄인다.
배제한 대안: ILIKE 순차 스캔만(인덱스 없음) — 19건엔 충분하나 '부분일치 인덱싱'이라는 교재 핵심 논점을 못 보여줌; 일반 btree 인덱스+ILIKE — 선행 와일드카드라 무효; PostGIS geography+GiST 거리 정렬 — 이 척도엔 과임이고 두 번째 확장 의존을 늘림.
트레이드오프: `pg_trgm` 확장 설치가 마이그레이션의 선행조건이 된다. 한글 완성형 음절의 trigram 동작(정밀도·재현성)은 3단계에서 실제 질의로 검증해야 한다 — 현재 미검증(이해하지 못한 부분). 19건에서 GIN 인덱스는 성능상 과임이며, 그 사실을 교재에 '운영 척도 대비 인덱스 설계'로 정직히 밝힌다. 하버사인은 순차 계산이라 데이터가 크게 늘면 공간 인덱스(PostGIS) 재검토가 필요하다.
