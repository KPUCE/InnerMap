# 완료의 정의 (Definition of Done)

이슈 하나가 '완료'가 되기 위한 공통 기준(#4). 수용 기준(AC)이 이슈마다 다른 "무엇"이라면, DoD는 모든 이슈에 같은 "어떻게 끝났는가"다. 번호 ①~⑥은 다른 문서(PR 템플릿, `pipeline-verification.md`, merge-gate 주석)가 참조하므로 바꾸지 않는다.

## DoD ①~⑥

| # | 항목 | 강제 주체 |
|---|---|---|
| ① | 수용 기준 전부 충족, 테스트 전부 통과(신규 테스트 포함) | CI(server-test·ios-build) + 리뷰(AC 대조) |
| ② | 변경 300줄 이하 — 초과 시 PR 분할, 불가피하면 PO 승인 하 `size:exempt` | CI(pr-size) |
| ③ | 작성자가 변경을 설명할 수 있다 — 리뷰의 설명 질문에 답하지 못하면 미완료 | 리뷰 |
| ④ | PR에 'AI 사용 내역'과 '이해하지 못한 부분'을 정직하게 기재 | PR 템플릿(필수 절) + 리뷰 |
| ⑤ | 설계가 바뀌었으면 새 ADR 추가(`docs/adr/`) — 기록되지 않은 설계 변경 금지 | 리뷰 |
| ⑥ | 시크릿·개인정보 미포함 — 키는 환경변수·Actions 시크릿만 | CI(secret-scan) + 리뷰 |

## 사람 검증 항목 (접근성 — 자동 검사가 잡지 못하는 것)

UI가 바뀌는 이슈는 위 ①~⑥에 더해 아래를 사람이 확인한다. 도구는 이해와 사용성을 측정하지 못한다(`pipeline-verification.md` "이 파이프라인이 잡지 못하는 결함").

- **접근성 자동 검사 위반 0건** (N-02) — Accessibility Inspector 감사 기준
- **모든 사용자 안내 텍스트가 접근성 알림으로 전달** (R-10)
- **핵심 흐름 VoiceOver 완주** (N-01) — 시뮬레이터 검증은 절반이다. 실기기 완주가 최종 기준이며, 시뮬레이터만 거쳤으면 PR에 그 사실을 명기한다(예: PR #30)
